# The golden evaluation set

## Status right now — read this first

`data/golden/golden_set.csv` in this repository ships **100% UNLABELLED**.
This sandbox has no network access to `kaggle.com` (confirmed directly —
see the README's earlier phases), so the real "Customer Support on
Twitter" dataset could never be downloaded here, no brand was ever chosen
from real data, and as a direct consequence **no genuine human labeling
was ever possible**. The shipped `golden_set.csv` was generated by
`scripts/create_golden_template.py` against the tiny synthetic test
fixture (`tests/fixtures/twcs_sample.csv`) purely to prove the tooling
works end to end — it has 2 rows, not the 150–250 (target 200) the
assignment calls for, and every `gold_*` cell is the literal string
`"UNLABELLED"`.

**This document describes what to do once the real dataset is available**:
re-run the sampling script against it, then hand-label the result following
the procedure below. Nothing in this document, and nothing in the shipped
CSV, should be read as if real labeling had already happened.

## Sampling procedure

`python scripts/create_golden_template.py --brand <brand> --target-size 200`:

1. **Candidate pool**: every individual customer message (one row per
   customer *turn*, not per resolved pair — unresolved/unanswered
   messages are valid candidates too) from conversations assigned to the
   **DEV or TEST** split. TRAIN-split conversations are never candidates —
   the golden set must never overlap what the retrieval corpus or any
   classifier's training data came from (`src.evaluation.run_eval`'s
   leakage checks enforce this automatically at evaluation time).

2. **Stratification signals** (computed once per candidate, using the
   *current* system purely as a labeling aid, never as ground truth):
   - `common_intent` / `rare_intent` — among the 3 most/least frequent
     system-*predicted* intents in the candidate pool.
   - `ambiguous` — system intent confidence below a low threshold
     (default 0.4).
   - `short_message` / `long_message` — word count at or below 4, or at
     or above 25.
   - `noisy_message` — URL-only, high non-letter character ratio, 3+
     `!`/`?` in a row, or mostly capitalized.
   - `missing_context` — currently aliased to `short_message` (a message
     too short to contain much concrete detail); a future iteration could
     use a smarter heuristic (e.g. absence of an order/ticket number
     pattern).
   - `predicted_escalate` / `predicted_auto_handle` — the current system's
     own `run_agent(...)` decision on this message, run with the mock LLM
     provider so no API key is required to generate the template.

3. **Sampling**: for each stratification bucket present in the pool, at
   least `target_size / (2 × number_of_buckets)` candidates are guaranteed
   a slot (subject to availability), then the remainder is filled with a
   seeded random sample from whatever's left, so every named category in
   the assignment (common/rare intents, ambiguous, short/long/noisy,
   missing-context, predicted-escalate, predicted-auto-handle) is
   represented, not just whichever categories happen to dominate the raw
   message distribution.

4. **Output**: `data/golden/golden_set.csv` with columns `example_id`,
   `conversation_id`, `customer_message`, `gold_intent`,
   `gold_should_escalate`, `gold_reason`, `gold_reply_quality`, `notes`.
   Every `gold_*` cell is the literal string `"UNLABELLED"`. `notes`
   contains the stratification bucket(s) and the system's *current*
   predicted intent/confidence/decision as a **suggestion only** — clearly
   labeled as such, never as a label, and the annotator is expected to
   form their own independent judgment rather than rubber-stamp it.

**Important**: this script does not call an LLM to guess what a human
annotator would write, and never invents a label under any circumstance.
The "system suggestions" in `notes` come from the actual classifier/
retrieval/escalation code already in this repo — the same code being
evaluated — not from a language model asked to role-play an annotator.

## Label definitions

### `gold_intent`

The single intent id from `configs/intents.yaml` (its `intents[].id`
values) that best describes what the customer is asking for, based on
reading the `customer_message` alone. If genuinely none of the taxonomy's
intents fit, use the taxonomy's configured `unknown_label` (currently
`other`) rather than inventing a new id — and separately, please flag it:
that's a sign the taxonomy itself is missing a category, which belongs in
`docs/GOLDEN_SET.md`'s "how to deal with ambiguity" workflow below, not a
silent guess.

### `gold_should_escalate`

`TRUE` or `FALSE` (also accepted: `true`/`false`, `yes`/`no`) — your
independent judgment of whether this message *should* be escalated to a
human agent rather than handled automatically, **based on the message
itself and general good judgment about what a responsible support
operation would do**, not based on what the system actually did. Concretely,
lean `TRUE` when:

- The issue involves money movement, account security, legal threats, or
  anything irreversible (refunds, cancellations, account deletion).
- The message expresses a safety or self-harm concern of any kind.
- The message is too vague/short to act on without asking a follow-up
  question.
- You genuinely can't tell what the customer wants (see "ambiguity"
  below).
- Resolving it correctly would require information a generic support
  agent (human or AI) plausibly wouldn't have without looking something
  up in an internal system this project has no access to.

Lean `FALSE` when the issue is a routine, low-risk, common question a
templated-but-personalized reply could reasonably handle (status inquiries,
general informational questions, acknowledging positive feedback).

### `gold_reason`

A short (one sentence is fine) free-text explanation of *why* you chose
the `gold_should_escalate` value above. This is what lets a later reader
(or the failure-analysis tooling) understand *why* a decision was
"correct," not just that it was — mirroring the same discipline
`src/agent/escalation.py`'s own rule engine applies to its own decisions.

### `gold_reply_quality`

A **1–5 score**, filled in during a **second labeling pass**, after
`python -m src.evaluation.run_eval` has been run at least once and produced
`artifacts/evaluation/predictions.jsonl` — because this label judges the
**system's actual drafted reply** for this example, which doesn't exist
until the system has been run. Scale:

- **5** — Correct, fully grounded in real evidence/the customer's message,
  appropriate tone, nothing fabricated, would be fine to send as-is.
- **4** — Solid and safe, minor stylistic issues only (slightly generic,
  could be warmer), nothing incorrect or fabricated.
- **3** — Acceptable as a stopgap but noticeably generic/unhelpful; not
  wrong, but wouldn't fully satisfy the customer.
- **2** — Meaningfully off: misses the point of the message, tone is
  wrong, or it's ungrounded speculation even if not technically false.
- **1** — Actively bad: fabricates a policy/refund/tracking number/date,
  claims an action was taken that wasn't, or is otherwise unsafe to send.

If the system escalated and drafted no reply at all, judge whether
escalating-without-replying was itself the right call given
`gold_should_escalate` — score 4–5 if escalating was appropriate and nothing
else went wrong, 1–2 if the system should have been able to draft a
reasonable reply instead.

`run_eval.py`'s "safe automation coverage" headline metric treats a score
of **4 or 5** as "acceptable" — see `docs/EVALUATION.md`.

### `notes`

Free text. The template pre-fills this with system-suggested stratification
info (see above) — feel free to append your own observations, but don't
delete the system-suggestion prefix; it's useful provenance for later
failure analysis.

## How to label it

1. Work through `gold_intent`, `gold_should_escalate`, and `gold_reason`
   **first, before running the system** (or without looking at
   `notes`'/predictions if you've already run it) — judge the raw
   `customer_message` on its own merits. This blind-first-pass ordering
   matters: if you read the system's predicted intent/decision before
   forming your own judgment, you're liable to anchor on it, which would
   quietly turn "does the system predict correctly" into "does the system
   predict what I told it to."
2. Run `python -m src.evaluation.run_eval` once all three of those columns
   are filled in.
3. Open `artifacts/evaluation/predictions.jsonl`, find each example's
   `final_system` row, read the actual drafted `reply`, and fill in
   `gold_reply_quality` for that row back in `golden_set.csv`.
4. Re-run `python -m src.evaluation.run_eval` — now every metric that
   depends on these labels (intent accuracy, escalation precision/recall,
   safe automation coverage) will compute a real number instead of
   reporting "pending."

## How to deal with ambiguity

Some messages will genuinely not have a clean answer. Don't force one:

- If **intent** is genuinely unclear between two categories, pick the one
  a support agent would act on first, and say so in `notes` (e.g. "could
  also be `refund_request`; leaning `billing_dispute` because the specific
  complaint is about being charged, not about wanting money back").
- If the **taxonomy has no good fit at all**, use `other` (the configured
  `unknown_label`) and note what category seems to be missing — this is
  real signal that `configs/intents.yaml` needs another pass, which is
  exactly the kind of thing this labeling exercise is supposed to surface.
- If you're unsure whether something **should escalate**, default to
  `TRUE` (escalate) — the cost of an unnecessary human review is much
  lower than the cost of a customer receiving a wrong/fabricated automated
  reply, and the project's whole design stance (see
  `src/agent/escalation.py`'s docstring) is to be conservative about
  automation.
- If a message is **too short or garbled to judge at all** (e.g. a single
  emoji, a test message, clearly not real customer support content), mark
  `gold_intent` as `other`, `gold_should_escalate` as `TRUE`, and say why
  in `notes` rather than guessing at real content that isn't there.

## How disagreements should be handled

If more than one person labels examples (recommended once real data
exists, precisely so agreement can be measured rather than assumed):

1. Label independently first — no discussing an example before both/all
   labelers have recorded their own answer. Otherwise you're measuring
   "did we discuss it into agreement," not "how much do independent
   judgments actually agree."
2. For any example where labels disagree, discuss and either converge on
   one answer or explicitly mark it `notes: "disputed — see discussion"`
   and keep both original judgments recorded somewhere (a spreadsheet
   comment, a linked doc) rather than silently overwriting one.
3. Report disagreement honestly rather than hiding it: a golden set with
   real inter-annotator disagreement recorded is more trustworthy than
   one that looks unanimous because disagreements were quietly resolved
   without a trace. This mirrors exactly the same principle behind
   `src/evaluation/judge_agreement.py`'s human/LLM-judge comparison — see
   `docs/EVALUATION.md`.
4. Never let the system's own predictions (in `notes`) break a tie. If two
   human labelers disagree and the system's suggestion matches one of
   them, that is not evidence for that side — it's simply a coincidence
   that needs its own independent scrutiny.
